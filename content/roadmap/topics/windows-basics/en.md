## The short version

Think of a Windows computer as an office building with a strict front desk.

- Everyone inside wears an **ID badge**: an **account**. Each badge carries a number that never changes, the **SID**,
  even if the name printed on it does.
- Badges list **departments**: **groups**, such as Administrators or Users. Doors are set up for departments, not for
  one person at a time.
- Every door and every cabinet has a list of who may open it and what they may do inside: **permissions**.
- The people working right now are **processes**. Each one wears a copy of somebody's badge and can do exactly what
  that person could.
- The night staff are **services**: they start before anyone arrives, and some carry the master key, the **SYSTEM**
  account.
- One huge binder holds every setting in the building: the **registry**. Timers on the wall start jobs at set times:
  **scheduled tasks**.
- The front desk writes everything important in a logbook: the **event logs**, which you read in **Event Viewer**.
- **PowerShell** is the intercom: you type questions and orders, and the building answers.

<mark>On Windows, every program runs as some account, and that account's groups and permissions decide what the
program can touch. An attacker who gets in tries to become a stronger account and to make their program start again by
itself.</mark> Almost everything defenders check on a Windows computer comes back to two questions: who is this running
as, and what starts it?

By the end of this page you'll be able to:

- say which account and groups a program runs as, and why the SID matters more than the name;
- explain what changes when you click **Yes** on a UAC prompt, and why UAC isn't a wall against malware;
- read a folder's permissions with `icacls` and work out who can change it;
- read a process tree and spot a parent and child that don't belong together;
- list services and scheduled tasks, and say which account runs each one and when;
- find your way around the registry, including the keys that start programs at logon;
- open Event Viewer and read a logon event (4624 or 4625);
- run everyday PowerShell commands and use `Get-Command`, `Get-Help` and `Get-Member` to find the rest.

## Words you'll need

- **Account:** a person's login, or a built-in identity such as SYSTEM that Windows itself uses.
- **SID (security identifier):** the unique ID behind every account and group, like `S-1-5-32-544`. Windows checks
  SIDs, not names.
- **Access token:** the badge a process carries: the account it runs as, its groups, its privileges and its integrity
  level. Every program you start gets a copy of yours.
- **Process:** a running program. While it runs, it has a number, the **PID** (process ID).
- **Service:** a program Windows starts and looks after in the background, often before anyone logs on.
- **Elevated:** running with full administrator rights, after **Run as administrator** and a click on **Yes**.
- **Registry:** Windows' database of settings, for the whole computer and for each user.
- **Command line:** the program and everything typed after it to start it. In an alert, it's often the most telling
  part.

> [!NOTE]
> This page uses Windows 11, whose current version, 26H2 (the Windows 11 2026 Update), came out on September 29, 2026.
> Nearly all of it holds for Windows 10 too, but Windows 10's support ended on October 14, 2025: no more security
> fixes unless the computer is enrolled in Microsoft's Extended Security Updates (ESU) program.

## Accounts, groups and SIDs

Everything on Windows happens on behalf of an account. A **local account** belongs to one computer and is kept on it, in
a database called the **SAM** (Security Account Manager), which also holds the account's password hash. At work, people
usually log on with an account from the company's directory instead, such as Active Directory, which comes later on the
path. Either way, the ideas below are the same.

### SIDs: the number behind the name

A SID looks like `S-1-5-21-1004336348-1177238915-682003330-1001` (this one is made up). The long middle part identifies
the computer or the domain; the last number, the **RID** (relative ID), identifies the account inside it:

- `500` is always the built-in Administrator account, and `501` the Guest account.
- Accounts that people create start at `1000`.

Renaming an account doesn't change its SID. Renaming Administrator to hide it fools nobody who looks at SIDs, and a tool
that checks names instead of SIDs can be fooled. A few SIDs are the same on every Windows computer in the world, and
they're worth knowing by heart:

| SID | Name | Who it means |
|---|---|---|
| `S-1-5-18` | SYSTEM (LocalSystem) | Windows itself and many services |
| `S-1-5-19` | LOCAL SERVICE | Services that need few rights |
| `S-1-5-20` | NETWORK SERVICE | Services that need few rights here but act as the computer on the network |
| `S-1-5-32-544` | Administrators | The computer's local admins |
| `S-1-5-32-545` | Users | Ordinary local users |
| `S-1-5-32-546` | Guests | The guest group |
| `S-1-1-0` | Everyone | A group that includes all users |
| `S-1-5-11` | Authenticated Users | Everyone who logged on with real credentials |

### The built-in accounts

Windows creates a few accounts during setup. Out of the box, most of them are switched off:

| Account | RID or SID | Out of the box |
|---|---|---|
| Administrator | `500` | Disabled. Setup creates your own admin account instead. It can't be deleted or locked out, only renamed or disabled. |
| Guest | `501` | Disabled, with a blank password. |
| DefaultAccount | `503` | Disabled. Windows uses it internally. |
| SYSTEM | `S-1-5-18` | Always there. Has full control of all files by default, and never shows up in the list of users. |

### Groups: rights that add up

Permissions are mostly given to groups, not to single people, and your rights are the sum of what your account and
all of your groups get. Membership of **Administrators** means control of the whole computer, so it's the group that
matters most.

<!-- pic: badge -->

> [!TIP]
> Microsoft recommends a different, random password for the local administrator on every computer, for example with
> **LAPS** (Local Administrator Password Solution). If every laptop shares one admin password, stealing it once opens
> them all.

## Administrators and UAC

Since Windows Vista, being an administrator doesn't mean every program you run has admin rights. **User Account
Control** (UAC) gives an administrator two tokens when they log on: a **standard** one, with the admin groups and
privileges taken out, and a **full** one. Explorer, the Windows desktop, runs with the standard token, and so does
everything you start from it. The full token is used only when you approve it.

<!-- pic: uac -->

- An administrator sees the **consent prompt** and clicks **Yes**. A standard user sees the **credential prompt** and
  has to type an administrator's name and password.
- The prompt appears on the **secure desktop**: the screen dims, and only Windows' own processes can reach it, so other
  programs can't click Yes for you.
- Buttons that need admin rights carry a **shield icon**. A gray prompt means a Windows program or a verified
  publisher; a yellow one means the program is unsigned or untrusted.

### Integrity levels

Every process also has an **integrity level**, a label that says how much it's trusted. Standard users and normal
programs run at **Medium**, elevated programs at **High**, services at **System**, and programs that handle risky content,
such as a web browser, at **Low**. A process can't change one at a higher level, even if the permissions would
otherwise allow it.

> [!WARNING]
> UAC isn't a wall. Microsoft lists it as a defense-in-depth feature, not a security boundary, and doesn't promise to fix
> ways around the prompt as security bugs. The real protection is simpler: everyday accounts shouldn't be
> administrators at all.

## Permissions: who may open which door

Every file, folder, registry key, service and process carries a **security descriptor**: its owner, and a **DACL**
(discretionary access control list). The DACL is a list of **ACEs** (access control entries), and each one says: this
SID is allowed, or denied, these rights.

When a process asks for access, Windows compares the SIDs in its token with the list:

1. If no entry matches any of your SIDs, you're denied. No entry means no access.
2. Entries apply in this order: **explicit deny**, **explicit allow**, **inherited deny**, **inherited allow**.
   Explicit means set on this object; inherited means passed down from the folder above.
3. Entries add up: you get what your account and every one of your groups get.

So an explicit deny beats everything, and an explicit allow on a file beats a deny it inherited from its folder.

### Reading icacls

`icacls` shows and changes permissions. Given only a path, it just shows them, one entry per line: who, then the rights
in brackets.

<!-- pic: acl -->

| Code | Right |
|---|---|
| `F` | Full control |
| `M` | Modify |
| `RX` | Read and execute (run) |
| `R` | Read only |
| `W` | Write only |
| `D` | Delete |
| `N` | No access |

The codes in brackets before the rights are about inheritance: `(OI)` means files inside get this entry, `(CI)`
subfolders get it, `(IO)` it applies only to what's inside, not to the folder itself, `(NP)` it isn't passed further
down, and `(I)` means this entry was inherited from the folder above.

### Folders worth knowing

| Folder | What's in it | Can a normal user change it? |
|---|---|---|
| `C:\Windows\System32` | Windows' own 64-bit programs and libraries (the "32" is historical) | No |
| `C:\Windows\SysWOW64` | The 32-bit versions; Windows sends 32-bit programs here when they ask for System32 | No |
| `C:\Program Files` | Installed programs | No |
| `C:\Users\<name>` | Your profile: Desktop, Documents, `AppData` and your part of the registry | Their own, yes |
| `C:\Users\<name>\AppData` | Programs' settings and data for one user | Yes, no admin rights needed |

This is why permissions matter in security work:

- A program that runs as SYSTEM from a file ordinary users can change is a door left open: replace the file, wait for
  it to start, and you're SYSTEM. Penetration testers check for this early, and defenders should too.
- Malware started by a normal user can't write to `System32` or `Program Files`, but it can write to that user's
  profile. A program in `AppData` that starts at every logon deserves a look.

## Processes: who's working right now

A process is a running program. For each one, Windows knows:

- its **PID**, a number that's reused once the process ends;
- its **image path**, the file it was started from;
- its **command line**;
- its **parent**: the process that started it;
- its **token**: the account, groups and integrity level it runs with.

You can see them in **Task Manager** (Ctrl+Shift+Esc, then the **Details** tab), with `tasklist`, or in PowerShell
with `Get-Process`. `Get-CimInstance Win32_Process` adds the parent's PID and the command line, the two things an
investigator wants first.

### Parents and children

Programs you start by clicking are children of **explorer.exe**, the desktop. Services are started by the **Service
Control Manager**, `services.exe`. Many Windows services are libraries that run inside **svchost.exe** (Service Host),
so a healthy computer has many svchost.exe processes, all started by services.exe, all from `C:\Windows\System32`.
`tasklist /svc` shows which services each one hosts.

<!-- pic: tree -->

> [!NOTE]
> Names lie. Attackers name their programs after Windows ones, such as svchost.exe, or put them in folders that look
> trusted. Others hide the real extension: `invoice.pdf.exe` shows as `invoice.pdf`, because Windows hides extensions
> for known file types by default. MITRE ATT&CK lists both tricks (T1036.005 and T1036.007).

### LSASS, the process attackers want most

`lsass.exe` (Local Security Authority Subsystem Service) checks who you are when you log on, and after a user logs on,
it keeps their credential material in its memory. That's why reading LSASS's memory is a classic attacker move (MITRE
ATT&CK T1003.001). Since Windows 8.1, Windows can run it as a protected process, so other programs can't read its memory
or inject code into it: **LSA protection**. On new installs of Windows 11 (version 22H2 and later) it's on by default
when the device meets Microsoft's requirements.

## Services: the night staff

A **service** is a program the Service Control Manager starts and looks after. The Service Control Manager itself starts
when Windows boots, then starts the services set to start automatically; others start when something asks for them.
Each service has a key under `HKLM\SYSTEM\CurrentControlSet\Services\<name>` with, among others:

- `ImagePath`: the program to run (for the svchost ones, `svchost.exe -k <group>`);
- `Start`: when it starts;
- `DisplayName` and `Description`: what you see in the Services window.

<!-- pic: starts -->

### Which account a service runs as

| Account | What it can do |
|---|---|
| LocalSystem | Almost anything on this computer; on the network it acts as the computer itself. |
| LocalService | Minimal rights here; anonymous on the network. |
| NetworkService | Minimal rights here; uses the computer's identity on the network. |
| A named account | Whatever rights that account has, for example a backup account. |

Services matter because they start before anyone logs on, often as SYSTEM. Creating a new service is a classic way to
make malware start at every boot (MITRE ATT&CK T1543.003). It's also a common way for an administrator to become
SYSTEM, because a service can be set to run as LocalSystem. `Get-Service` lists the services; `Get-CimInstance Win32_Service` adds each one's
start mode, account (`StartName`) and program (`PathName`).

## The registry: one binder of settings

The registry is a tree. **Keys** work like folders; inside them, **values** each have a name, a type and data. It has
five root keys:

| Root key | Short name | What's in it |
|---|---|---|
| `HKEY_LOCAL_MACHINE` | HKLM | Settings for the whole computer |
| `HKEY_CURRENT_USER` | HKCU | Settings of the user who's logged on: a shortcut to their own branch of HKU |
| `HKEY_USERS` | HKU | Every user profile that's loaded |
| `HKEY_CLASSES_ROOT` | HKCR | File types and the programs that open them |
| `HKEY_CURRENT_CONFIG` | HKCC | The hardware profile in use |

The common value types are `REG_SZ` (text), `REG_EXPAND_SZ` (text with variables such as `%SystemRoot%`),
`REG_MULTI_SZ` (a list of texts), `REG_DWORD` (a 32-bit number), `REG_QWORD` (a 64-bit number) and `REG_BINARY` (raw
bytes).

### Hives: the registry on disk

The registry is kept in files called **hives**. The computer-wide ones are in `C:\Windows\System32\config`; each
user's own part is a file in their profile folder. HKCU is the user's own file, so a normal user can change most of
it; most of HKLM needs admin rights.

<!-- pic: hives -->

The **SAM** hive holds local accounts and their password hashes. Attackers with admin or SYSTEM rights copy it, often
together with the SYSTEM hive, with `reg save` (MITRE ATT&CK T1003.002), so a `reg save HKLM\sam` you didn't expect is
a red flag.

> [!WARNING]
> Look, don't touch. Microsoft warns that changing the registry incorrectly can cause serious problems, some of which
> mean reinstalling Windows. Reading is always safe.

### Keys that start programs

The best-known autostart keys are **Run** and **RunOnce**, in both HKLM and HKCU under
`Software\Microsoft\Windows\CurrentVersion`. A value under **Run** starts its program every time the user logs on; a
value under **RunOnce** runs once and is deleted, by default before its command even starts. Each value's data is a
command line of up to 260 characters. By default these keys are ignored in Safe Mode.

Two folders work the same way. A program or shortcut in
`C:\Users\<name>\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup` opens when that user logs on,
and one in `C:\ProgramData\Microsoft\Windows\Start Menu\Programs\StartUp` opens when anyone logs on.

<!-- pic: autostart -->

## Scheduled tasks: the timers

**Task Scheduler** runs a task when its **trigger** fires: a time or a schedule, startup, logon, idle time, or an event
appearing in a log. Each task has one or more **actions**, usually "run this program with these arguments", and runs as
a chosen account: the user who made it, SYSTEM, or another account. A normal user can create tasks that run as
themselves, without admin rights.

Windows keeps every task as an XML definition. `schtasks /query /xml` prints it, and investigators also find these
definitions as files under `C:\Windows\System32\Tasks`. Most of Windows' own tasks live in the `\Microsoft\Windows\`
folder of Task Scheduler, so a task outside `\Microsoft\` is the first kind to look at. Attackers use tasks to start
their programs on a schedule (MITRE ATT&CK T1053.005), and as with processes, a familiar name proves nothing: check what
a task actually runs.

## Event Viewer: the logbook

Open **Event Viewer** by typing `eventvwr.msc` in the Start menu. The logs you'll use most are under **Windows Logs**:

- **Application:** messages from programs.
- **Security:** audit events, such as logons, recorded as success or failure. Only administrators can read it.
- **Setup:** events about setup and installation.
- **System:** events from Windows itself and its services, such as a service that failed to start.
- **Forwarded Events:** events sent from other computers, if someone set that up.

Under **Applications and Services Logs**, each app and many parts of Windows (PowerShell and Task Scheduler among them)
keep their own log. Every log is a `.evtx` file in `C:\Windows\System32\winevt\Logs`. In Application and System, events
have levels: **Error**, **Warning** and **Information**.

> [!NOTE]
> Unless a policy says otherwise, the main logs are 20 MB each, and Microsoft now recommends much more (4 GB). On a busy
> computer, 20 MB doesn't reach back far, so an investigation can find the logs it needed already gone.

### Reading a logon

With logon auditing on, Windows writes **4624** when an account logs on successfully and **4625** when it fails, both in
the Security log. The **Logon Type** in each one says how:

| Logon Type | Name | Usually means |
|---|---|---|
| 2 | Interactive | Someone at the keyboard |
| 3 | Network | Access over the network, such as a shared folder |
| 4 | Batch | A scheduled task or another batch job |
| 5 | Service | A service starting |
| 7 | Unlock | The screen being unlocked |
| 10 | RemoteInteractive | Remote Desktop |
| 11 | CachedInteractive | A domain account logging on with saved credentials, no domain controller reached |

<!-- pic: logon -->

In a 4625, the **Status** and **Sub Status** codes say why it failed: `0xC000006A` a wrong password, `0xC0000064` a
user name that doesn't exist (many in a row look like someone hunting for valid names), `0xC0000234` a locked account. Which other events
matter, and how to collect them, is a topic of its own further down the path: Windows event logs and Sysmon.

## PowerShell: the intercom

PowerShell is a command line and a scripting language in one. There are two of them, and they live side by side:

| | Windows PowerShell 5.1 | PowerShell 7 |
|---|---|---|
| Comes with | Windows, since the Windows 10 Anniversary Update (August 2016) | A separate install |
| Program | `powershell.exe` | `pwsh.exe` |
| Runs on | Windows | Windows, macOS and Linux |
| Support | As long as your Windows is supported | 7.6, the current long-term release: March 18, 2026 to November 14, 2028 |

Windows PowerShell lives in `C:\Windows\System32\WindowsPowerShell\v1.0`, and PowerShell 7 installs to
`C:\Program Files\PowerShell\7`. Everything on this page works in the Windows PowerShell that's already on your
computer.

### How commands look

Commands, called **cmdlets**, are named **verb-noun**: `Get-Process`, `Get-Service`, `Stop-Service`. Options start with a
dash: `Get-Service -Name EventLog`. The old commands still work too: `whoami`, `tasklist`, `icacls` and `ipconfig` run
from PowerShell as they do anywhere else.

The big difference from other shells is the **pipeline**. The `|` passes whole objects from one command to the next,
not just text, so you can sort, filter and pick fields by name:

```powershell
Get-Process | Sort-Object CPU -Descending | Select-Object -First 5 Name, Id, CPU
Get-Service | Where-Object Status -eq 'Running'
```

The first line shows the five processes that have used the most processor time; the second, every running service.

### Three commands that find all the others

- `Get-Command` lists commands: `Get-Command -Noun Service` shows every command about services.
- `Get-Help` explains one: `Get-Help Get-Service`. Help files don't come preinstalled, so the first time PowerShell may
  offer to download them; `-Online` opens the page on Microsoft Learn instead.
- `Get-Member` shows what an object is made of: `Get-Service | Get-Member` lists every property you can sort or filter
  on.

> [!WARNING]
> The **execution policy** decides whether PowerShell script files may run on Windows, and whether they need a signature.
> Microsoft says it plainly: it isn't a security boundary. Anyone can type a script's contents at the prompt instead.
> Attackers use PowerShell for the same reason admins do: it comes with Windows and can do almost anything.

## How it shows up on the job

Here's a made-up alert of the kind an endpoint protection tool (EDR) raises every day:

```
Made-up EDR alert · LAPTOP-07 · 2026-11-12 09:41 UTC
Rule: Office application started a script interpreter

explorer.exe (4812)            LAPTOP-07\alex · Medium
└─ WINWORD.EXE (7340)          "C:\Users\alex\Downloads\Invoice_7741.docm"
   └─ powershell.exe (7712)    -NoProfile -WindowStyle Hidden -EncodedCommand JABjAD0A…
      ├─ file created    C:\Users\alex\AppData\Roaming\UpdateHelper\updhelper.exe
      ├─ registry value  HKCU\Software\Microsoft\Windows\CurrentVersion\Run
      │                  UpdateHelper = C:\Users\alex\AppData\Roaming\UpdateHelper\updhelper.exe
      └─ schtasks.exe (7790)  /create /tn UpdateHelper /tr C:\Users\alex\AppData\Roaming\UpdateHelper\updhelper.exe /sc daily /st 09:00
```

Read it from the top:

1. **explorer.exe → WINWORD.EXE:** Alex opened a document from Downloads. Normal so far, except that `.docm` is a Word
   document that can carry macros.
2. **WINWORD.EXE → powershell.exe:** Word has no everyday reason to start PowerShell. This pair is why the alert fired.
3. **The command line:** no window (`-WindowStyle Hidden`) and a script encoded so it can't be read at a glance
   (`-EncodedCommand`). Decoding it is the next step.
4. **A program in AppData\Roaming:** a folder Alex can write to without admin rights.
5. **A Run value in HKCU:** the program now starts at every logon of Alex's, again without admin rights.
6. **A scheduled task:** a second way back in, every day at 09:00, in case someone deletes the Run value.
7. **Medium, as alex:** so far the attacker has Alex's rights, not admin. The next questions are whether anything tried
   to get admin or SYSTEM rights, touched `lsass.exe`, or logged on to other computers with Alex's account (4624 events).

On a real case, you'd isolate the laptop and collect the file, the Run value and the task as evidence before removing
anything.

- **Security operations (SOC):** you triage alerts like this one every day: parent and child, command line, account,
  integrity level, then a decision.
- **Incident response and forensics:** you find every autostart entry (Autoruns does it in one go), read the hives from
  a disk image, including each user's NTUSER.DAT, and rebuild the timeline from event logs and task definitions.
- **Penetration testing and red teaming:** with permission, you check what your account can do, look for services and
  folders with weak permissions, and see whether LSASS is protected.
- **Detection engineering and threat hunting:** you write rules for odd parent-child pairs, new Run values, new services
  and new scheduled tasks, and you hunt for the ones nobody can explain.
- **Security administration and endpoint security:** you take admin rights away from everyday accounts, give every
  computer its own local admin password, turn on LSA protection and make sure the logs are big enough to be useful.
- **Malware analysis:** you watch which accounts, keys, services and tasks a sample creates, because that's what a
  defender will search for.

## Try it yourself

Twenty minutes on a Windows computer. Every command here only reads; none of them changes anything.

### Your badge and your rights

<!-- for: windows -->

Open PowerShell: type `powershell` in the Start menu and press Enter. Then run:

```powershell
whoami /groups
Get-LocalGroupMember -SID S-1-5-32-544
icacls $env:USERPROFILE
icacls C:\Windows\System32\drivers\etc\hosts
```

In the first output, find `BUILTIN\Administrators` and the `Mandatory Label` line. If you're an administrator, the group
says "Group used for deny only" and the label says Medium. Now right-click PowerShell, choose **Run as administrator**,
click **Yes** and run `whoami /groups` again: what changed?

`Get-LocalGroupMember` lists the local admins. It asks for the group by its SID, so it works on Windows in any language,
where the group's name is translated. Look at the **PrincipalSource** column: Local, Active Directory, Microsoft Entra
group or Microsoft Account. Then compare the two `icacls` outputs: who has `(F)` on your profile folder, and who can
change the `hosts` file?

<!-- for: macos, linux -->

PowerShell 7 runs on macOS and Linux too, so you can practice the PowerShell part there: run `pwsh`, then
`Get-Command`, `Get-Help Get-Process` and `Get-Process | Get-Member`. Accounts, services, the registry and Event Viewer,
though, exist only on Windows.

For everything else in this section, build a free Windows 11 trial in a virtual machine: on Linux, VirtualBox works
well. On a Mac with Apple silicon (M1 or later), use a Windows 11 for Arm machine instead, because x86 Windows only runs
emulated there, and slowly; the [lab's Get started](/en/lab/start/) compares the options.
<!-- guide: set-up-windows-trial-vmware, set-up-windows-trial-virtualbox -->

### Who started whom

```powershell
Get-CimInstance Win32_Process -Filter "ProcessId=$PID" | Select-Object Name, ParentProcessId, CommandLine
tasklist /svc /fi "imagename eq svchost.exe"
Get-CimInstance Win32_Service -Filter "State='Running'" | Sort-Object StartName | Select-Object Name, StartName
```

The first command describes the PowerShell you're typing in (`$PID` is its own process ID). Take its
**ParentProcessId** and run `Get-Process -Id` with that number: which program started your PowerShell? The second lists
every svchost.exe with the services inside it. The third lists the running services by account: which accounts do you
see, and how many services run as LocalSystem?

### What starts by itself

```powershell
Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Run
Get-ItemProperty HKLM:\Software\Microsoft\Windows\CurrentVersion\Run
Get-ScheduledTask | Where-Object TaskPath -notlike '\Microsoft\*'
```

In the Run keys, skip the lines that start with `PS`: PowerShell adds those. Every other line is a program that starts
at logon. Do you recognize each one? Then pick a task from the last list and see what it runs:
`(Get-ScheduledTask -TaskName 'its name').Actions`. If you want everything in one window, download Microsoft's free
**Autoruns** (Sysinternals) and look at its **Logon** and **Scheduled Tasks** tabs.

### Read the logbook

Open Event Viewer (`eventvwr.msc`), go to **Windows Logs** > **System** and look at the newest events and their levels.
Then, in PowerShell:

```powershell
Get-WinEvent -LogName System -MaxEvents 10
```

The Security log needs an administrator window. In one, run:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624} -MaxEvents 5 | Format-List TimeCreated, Message
```

Find the **Logon Type** in each event. You'll probably see many of type 5: services starting. Why would a computer log
so many of those?
