Програми на Java постійно отримують Base64: заголовки входу, повідомлення SAML і токени безпеки записують дані саме так, 64 звичайними символами. Щоб декодувати швидше, Java має написаний вручну «швидкий шлях» для процесорів x86-64 з інструкціями AVX-512 VBMI. 17 листопада 2026 року Oracle і проєкт OpenJDK виправили CVE-2026-114938 — ваду в цьому шляху. Довгий рядок Base64 з незвичним доповненням `=` в кінці змушує Java записати 62 чи 63 байти за межею свого вихідного буфера. Java цей рядок таки відхиляє, але вже після запису.

Ваду знайшла й розкрила компанія Calif, і вона отримала прізвисько Java4Shell. Вона зачіпає Java 17.0.6 і новіші, а також Java 21, 25 і 27 від усіх основних постачальників, але лише на процесорах із цим набором інструкцій: Intel Xeon, починаючи з Ice Lake, і AMD Zen 4 та новіших. Java 8 і 11 та сервери на ARM вада не зачіпає. Calif каже, що зібрала ланцюжки, які захоплюють шість застосунків без пароля, зокрема Keycloak, Jira, Confluence, Jenkins, JFrog Artifactory і PingFederate, і ще п'ять після входу, а пізніші ланцюжки ШІ-агенти зібрали майже самостійно. Компанія їх не публікувала.

Перетворити ваду на виконання коду складно. VulnCheck пояснює, що для цього треба ретельно впорядкувати пам'ять і ще окремо отримати витік, щоб обійти рандомізацію адрес, а Oracle оцінює складність атаки як високу. Зате спричинити збій легко, і Calif каже, що за обережного використання вада ще й видає вміст пам'яті. Інші команди відтворили ваду: Blackpoint Cyber обвалила тестовий застосунок на Spring Boot приблизно 28 300 хибними запитами на вхід приблизно за 20 секунд, а VulnCheck увечері 17 листопада передала клієнтам повний експлойт. До 22 листопада про атаки не повідомляли, але watchTowr оцінює їх як дуже ймовірні.
